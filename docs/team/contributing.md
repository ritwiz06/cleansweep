# Contributing

How a change gets from your machine into `main`. The same rules apply to all four of us.

## The workflow

1. **Pick an issue** from [tasks.md](tasks.md), or open one for a problem you found.
2. **Branch from an up-to-date `main`**, with the area as the prefix:

   ```bash
   git switch main
   git pull
   git switch -c data/tiers-table-subset
   ```

   | Prefix | Area | Typical files |
   |---|---|---|
   | `core/` | software architecture | `src/cleansweep/` (llm, sandbox, guard, workflow, agents), `configs/base.yaml` |
   | `data/` | data | `src/cleansweep/data/`, `src/cleansweep/mining/`, `scripts/data/`, `data/splits/`, `results/data_summary/` |
   | `exp/` | experiments | `scripts/experiments/`, `src/cleansweep/eval/`, `results/summary/`, `results/figures/` |
   | `rev/` | Reviewer, docs and releases | `src/cleansweep/reviewer/`, `docs/`, `CHANGELOG.md`, the pre-registration |
   | `app/` | Studio and the demo | `app/studio/`, `demo/` |

3. **Commit in small steps** under your own name and email (`git config user.name`,
   `git config user.email`), so [contributions.md](contributions.md) can credit you. Write
   messages like the history does: `data: tiers table includes the Phase 2 subset`.
4. **Run the checks** (below). The pre-push hook runs them for you if you installed it
   ([setup.md](setup.md#install-the-pre-push-checks)).
5. **Push and open one pull request:**

   ```bash
   git push -u origin data/tiers-table-subset
   gh pr create --title "data: tiers table includes the Phase 2 subset" --body "Closes #NN. ..."
   ```

   The title starts with the area. The description says what changed, why, how you tested it,
   and which issue it closes.
6. **Review and merge.** Ritik reviews, and merges with a merge commit once the checks pass.
   Never push to `main` directly, never force-push, never rewrite `main`'s history.

## Pull request checklist

- [ ] The branch name has its area prefix, and the PR title starts with the area.
- [ ] `ruff check .`, the offline tests and the contract check pass.
- [ ] New code has tests in the `tests/` folder that mirrors it; tests that need the LLM,
      Docker, the network or a long time are marked.
- [ ] Changes to `src/cleansweep/core/models.py` or `core/contracts.py` only add things.
- [ ] Nothing secret or local is committed: no `.env`, no keys, no data files, no
      `results/raw/`, no absolute paths from your machine.
- [ ] No names of AI assistants or coding tools, no "generated by" notes and no co-author lines
      in code, comments, docs, commit messages or the PR description.
- [ ] If a committed table changed, the script that writes it was rerun, and the docs that
      quote its numbers were updated.
- [ ] The PR closes its issue, and [contributions.md](contributions.md) has a row for it.
- [ ] The PR is reviewable: about 400 changed lines or fewer where possible.

## Running the checks

From the repository root, with the environment active:

```bash
ruff check .
pytest -q -m "not llm and not docker and not network and not slow"
python scripts/tools/check_contracts.py
```

These are the same three checks CI runs on every pull request. If you pipe a check's output
(for example into `tail`), add `set -o pipefail` first, or the pipe hides a failure.

Other checks, when your change touches them:

| Change | Also run |
|---|---|
| a table or figure | `bash scripts/reproduce_tables.sh`, then `git status --short results/` shows only what you meant to change |
| `agents/` or `guard/` | `bash scripts/tools/coverage.sh` (fails under 80%) |
| Studio's frontend | in `app/studio/frontend`: `npm run build`, `npx vitest run`, `npx playwright test` |
| anything that needs a key or Docker | the marked tests for it, for example `pytest -q -m docker tests/sandbox/test_container.py` |

## Where tests go

- One test file per module, in the folder that mirrors the code:
  `src/cleansweep/guard/difftest.py` is tested in `tests/guard/test_difftest.py`.
- Scripts: `scripts/experiments/v3/exp_real_v3.py` is tested in
  `tests/scripts/experiments/v3/test_real_v3.py`. Studio's API: `tests/app/studio/`.
- Shared fixtures (the toy repository, the answer key, a small results set) are in
  `tests/fixtures/`.
- Markers: `llm` (calls the Voyager API), `docker`, `network`, `slow`. Unmarked tests must run
  offline in seconds.
- In fixtures, use neutral agent names such as `agent_a` and `agent_b`. Build fake credentials
  from parts at run time; never write a key-shaped string as a literal (a secret scanner flagged
  fake test keys once).
- `tests/test_repo_layout.py` fails when a tracked file is not where
  [repo_layout.md](../repo_layout.md) says, or is named like scratch (`tmp_*`, `*_old`,
  `*_backup*`, `scratch*`, `*.bak`, `untitled*`, `debug_*`).

## Updating results and docs

- **Never edit a committed table by hand.** Rerun the script that writes it;
  [experiments.md](../experiments.md#regenerating-the-tables) lists every file and its script.
- **The aggregate tables rebuild offline:** `bash scripts/reproduce_tables.sh`. On a clean
  checkout, `git status results/` shows no change afterwards. If it shows one, that is a finding:
  open an issue.
- **After the freeze (Nov 13, 12:00), the Phase 3 tables are final.** A mistake found later is
  fixed in its own pull request that says what changed and why, and the report says so too.
  Nothing is changed quietly.
- **Docs:** plain English, Phase 1, 2 and 3 instead of version numbers, every number with the
  file it comes from, and "LLM-judged" on anything a model decided. Check that your links work.
- **Never commit** `.env`, `data/raw/`, `data/processed/`, `results/raw/`, `.cleansweep/` or
  `.notes/`. Git ignores most of these; `.notes/` is the exception, so leave it out of
  `git add`. One data script writes a file there (see [tasks.md](tasks.md)).
